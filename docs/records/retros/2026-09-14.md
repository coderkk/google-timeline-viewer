### 什么做得不好（本次沟通/token 成本高的主因）
- **需求没对齐就动手**：用户只说「看 2025-01-30」，我直接改 segment fallback（T16），没先问「你期待看到什麼」。结果 T16→T16.1→T16.2→T17 四轮返工，其实一轮可完成。
- **没先验证资料格式**：我查了 rawSignals，却没查 `timelinePath` 有 `time`——那正是用户点名的档案里就有的栏位，到 T17 才发现。
- **反复全量验证**：每次「reload + 汇入 123MB」约 20s，做了十几次。UI 其实可用 sample data 秒级验证，资料正确性可用 node/vitest 直读真档。
- **注入 debug 码**：把 `__DEBUG_FIT` console.log 加进 app，还因 HMR 没生效耗掉好几轮。诊断应写 `scripts/` 一次性脚本或测试。
- **HMR race**：同一档案分多次编辑，中间态坏掉 → 误报 error → 又 reload，白费轮次。
- **用 canvas 像素数当验证**：反复 `getImageData` 扫蓝点，绕且不直观。
- **不问、自己决定**：资料结构、颜色、UI 行为都我单方面拍板，用户只能一轮轮纠正——用户原话：「你好像有東西不明白，但是又不問。常常一直用自己的方法。」
- **PRD 没有先行**：T16–T17 的 PRD 是**做完才补写**（违反 workflow 规则 #2「PRD 先行，代码是流」）；而且功能 3 **本体没同步**，一度留下已被 T17 推翻的「按本地日分桶」描述 → PRD 与实作自相矛盾；验收条件也没补（时间、可点链接、左栏时间线）。是用户问「還有PRD有做嗎？」才发现的。
