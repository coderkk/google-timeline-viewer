# Google Timeline 資料格式逆向筆記：同一份 JSON、兩種導出、三個工程陷阱

> 原文日期：2026-09-14　|　系列：Google Timeline 資料格式實戰

## TL;DR

- Android「時間軸」內建導出與 Google Takeout，產出的是**同一種新版扁平 JSON 格式**（`semanticSegments` / `rawSignals` / `userLocationProfile`，逐欄位一致）。以為兩種管道格式不同，是常見誤解。
- `semanticSegments` 是**永久歷史**（本案例 13 年）；`rawSignals` 只有**導出前約 30 天**的滾動窗口，過期被伺服器清除，任何導出方式都拿不回。
- 要留高密度原始軌跡，唯一方法是**每 ≤30 天導出並存檔**，多次導出天然互補、可去重合併。
- 真正的坑在**時區分組**與**軌跡匹配語義**：前者把凌晨資料標到前一天，後者曾讓 64% 的中途行程斷線。

---

## 背景：為什麼需要逆向

[google-timeline-viewer](https://coderkk.github.io/google-timeline-viewer/) 是純前端、完全在本機渲染的 Google Timeline 檢視器。開發時最大的阻礙是**沒有官方文件**：locationhistoryformat.com 只描述舊版 Takeout，新版扁平結構（`semanticSegments` 體系）沒有正式規格，只能從真實導出資料反推。我們手上正好有兩份相隔一年半的真實檔案：

| 檔案 | 來源 | 導出日期 | semanticSegments | rawSignals |
|---|---|---|---|---|
| `Timeline-20250213.json` | Google Takeout | 2025-02-13 | 83,202 段（2012-12-30 → 2025-02-13） | 50,662 條（2025-01-14 → 02-13，恰 29 天） |
| `Timeline-20260820.json` | Android 內建導出 | 2026-08-20 | 97,382 段（2012-12-30 → 2026-08-20） | 55,509 條（2026-07-21 → 08-20，恰 29 天） |

以下發現全部來自兩份檔案的逐欄位比對。

---

## 發現一：兩種導出方式輸出同一份格式

兩份檔案頂層結構一模一樣，schema 的所有 key 逐項相同：

```jsonc
{
  "semanticSegments": [ ... ],   // visit / activity / timelinePath / timelineMemory
  "rawSignals": [ ... ],         // position / wifiScan / activityRecord
  "userLocationProfile": { ... } // frequentPlaces / frequentTrips / persona
}
```

**導出方式不影響格式**，但同一天的語義資料仍有三種「合理差異」，值得注意：

- **分割粒度**：2025-01-31 有 28 段 vs 30 段——後導出者把同一行程的 3 小段合併成 1 大段，資料不衝突；
- **欄位豐富度**：同一停留點 visit 的 JSON 長度 255 vs 246，後導出補上概率等運算 metadata；
- **activity 重分類**：同一段（11:03:08）2026 版是 `IN_BUS`、2025 版是 `IN_PASSENGER_VEHICLE`——**`activityType` 不是穩定識別碼**，不能當去重鍵或長期分析的維度。

## 發現二：semanticSegments 是永久歷史，rawSignals 只有 30 天

**semanticSegments 是長期永久資料**：兩份檔案都含 2012-12-30 起完整的 13 年地圖匹配軌跡，隨時導出都在。

**rawSignals 是導出前約 30 天的滾動窗口**（兩份檔案都恰為 29 天）。證據鏈很乾脆：

- 2025-02-13 導出時，`2025-01-14 → 02-13` 的原始訊號存在；
- 2026-08-20 再導出時只剩下 `2026-07-21 → 08-20`，同一天 2025-01-30 的原始訊號**徹底消失**。

輔證：2026 那份檔案針對 2026-01-30 完全沒有 rawSignals，當天只剩 timelinePath 可用。

### 工程啟示：最基本的存檔策略

要累積高密度原始 GPS 軌跡，必須**定期（≤30 天）導出並存檔**。每次的 rawSignals 窗口互不重疊、天然互補，合併去重即得連續高密度原始軌跡；只看完整路線則任意一次導出即夠。這是唯一可行的對抗滾動窗口策略。

## 發現三：時區陷阱——資料沒丟，只是分錯組

App 內部有兩套日期口徑打架：

| 環節 | 實作 | 時區口徑 |
|---|---|---|
| 日期篩選器（使用者點「2025-01-30」） | `parseInputDate` | **本地（+08）** 零點 |
| 段時間戳解析 | ISO 帶偏移 → UTC epoch | 正確 |
| 地圖「同一天」高亮分組 | `startOfDayMs`（`getUTC*`） | **UTC 日** |
| 日期跨度統計 | `dayKeyOf`（`toISOString`） | **UTC 日** |

篩選本身不丟資料（+08 的 2025-01-30 = UTC `[01-29 16:00Z, 01-30 15:59Z]`），但分組函數用 UTC 日，凌晨 `00:00–07:59`（+08）的段被歸到 UTC「前一天」。實測 2025-01-30 有 3 段（+08 時間 `01-29 22:00 / 01-30 04:00 / 01-30 06:00`）全被標到 01-29——使用者覺得「當天少了凌晨資料」，其實只是側欄分組與地圖高亮的口徑錯了一格。

**教訓**：日期分組、側欄、地圖高亮必須與篩選口徑（本地時區）一致，用 `getFullYear/getMonth/getDate`，而非 `getUTC*`/`toISOString`。

## 發現四：路線縫合——端點恆等是錯的，最近點才是對的

新版格式中 `timelinePath` 與 `activity` 是**兩種粒度**的資料：前者是跨整個 **2 小時窗口的連續軌跡**（平均 ~10 點，實測 min 1 / max 106）；後者只是窗口內**其中一段短途**（如 16:15–16:33 只佔 16:00–18:00 trace 的第 0–4 點），且只帶起終點，沒有中間軌跡。

初版縫合要求 **activity 端點 ≡ trace 首/末點**，結果約 **64% 的中途行程縫合失敗**（path = 0）。改進後的語義：在 trace 內找與 start/end **幾何最近的點對**（`isNear ≤ 0.02°` ≈ 2km），取子段 `slice(i, j+1)`；`i == j` 拒絕單點退化；反向極端配對兼容；保留時間重疊閘門防跨時段誤縫。

效果：2026-01-30 從 16/17 段有路 → **17/17**，16:15 那段 path 0 → 5（精確覆蓋 16:15–16:33）。單 trace 平均 10 點、三萬條級的量用二分 + 前綴扇出，效能無虞。

**教訓**：匹配要按「最近點 + 時間重疊」，而非「端點恆等」——端點恆等只在語義段完整覆蓋資料源時成立，凡語義段是資料源子集者必然系統性失敗。

---

## 教訓與最佳實踐

1. **對抗滾動窗口靠存檔紀律**：凡是「只留近期」的雲端資料，都要定義匯出週期（這裡是 ≤30 天）、定期存檔、按時間指紋去重合併；等需要時再導一次，歷史已拿不回。
2. **日期分組、篩選、統計用同一套時區口徑**：混合 UTC 與本地時區的典型症狀是「邊界時段的資料不見了」——先追「是不是分錯組」，再懷疑資料缺失。
3. **語義匹配依賴最近性與重疊，不依賴恆等**：資料源粒度、語義粒度、顯示粒度是三件事；先確認語義段是否為資料源子集，再決定匹配策略。同理，`activityType` 這類衍生分類不穩定，別拿來當識別碼。
