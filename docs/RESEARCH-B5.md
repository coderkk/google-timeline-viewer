## 〇、先讲一个故事（你 10 秒能懂）

想象你的手机是**一个很笨但很勤快的记录员**。它记录你的生活，用的三种本子：

| 本子 | 记录什么 | 频率 | 例子 |
|------|---------|------|------|
| **停留本（visit）** | 你**待着不动**的地方 | 你离开时才写一笔 | 「在表哥家，17:00–22:00」 |
| **出行本（activity）** | 你**在移动**的线路 | 每次移动写一笔 | 「驾车，从表哥家到机场，22:00–23:30」 |
| **巡逻本（timelinePath）** | 手机**每 2 小时自动探查一次**你在哪 | 固定 2 小时一次，风雨无阻 | 「02:00 你在表哥家方圆 500m；04:00 还在」 |

三种本子分开记，**互不商量**。这就是后面所有「怪现象」的根源。

我们这个产品（你的私人旅行回忆地图）读的是这三种本子的档案，其中「行程链」功能（T29）想把它们拼回你真实的一天：「停留 → 移动 → 停留」的旅行日记。侦察就是回答一个问题：**这个笨记录员的本子，到底能不能拼出真实的样子？**

## 一、第一课：读懂 Google Timeline 的数据

### 1.1 三种记录的真实长相

Google 把所有记录装在一个叫 `semanticSegments`（语义段）的数组里，一条记录就是「一小段时间里你在做什么」。三种记录：

```jsonc
// ① 停留（visit）——你在一个地方待着
{ "startTime": "2024-02-11T13:39:57+08:00", "endTime": "...",
  "visit": { "topCandidate": { "placeLocation": {...}, "semanticType": "HOME" } } }

// ② 出行（activity）——你在移动，有明确的起终点
{ "startTime": "...", "endTime": "...",
  "activity": { "start": {...}, "end": {...}, "topCandidate": { "type": "IN_VEHICLE" } } }

// ③ 巡逻（timelinePath array）——只有一段 GPS 轨迹点，没有起终点语义
{ "startTime": "...", "endTime": "...", "timelinePath": [ {"point": "...", "timestampMs": ...}, ... ] }
```

观察一下三种记录的特点，这份直觉后面全用得上：

- **visit 和 activity 是「语义」**：Google 判断出了你「在停留」还是「在移动」，还给了语义类型（家/工作/驾车/步行/飞机…）。
- **timelinePath 是「物理」**：它没有任何语义判断，就是**一段原始 GPS 坐标轨迹**。
- **关键**：`activity` 段**有时也带** `timelinePath`（精细移动轨迹），巡逻段是**只有** timelinePath、没有 activity 语义 的「孤儿」GPS 窗口。

> 🧠 记着：**有语义的段（①②）和纯物理的段（③）是两类东西。** 这个区分是整篇报告的钥匙。

### 1.2 我们的产品怎么读这些数据

产品解析器（`parse/common.ts`）把「有起终点的时间块」都压成统一的 `Segment`，塞给两个功能：

- **时间轴模式**（默认）：把 GPS 点按时间排成一条连续的「走过的路」（合并 rawSignals + timelinePath 点，按时间排序去重）。它读的是**物理点**，天生不在乎语义。
- **「按活动类型」模式**：走 **行程链（T29 / PRD 功能 13）**——把停留和移动段串成「停留 → 移动 → 停留」的日记。它读的是**时间段**。

问题就出在：**解析器当年为了时间轴模式把 ③孤儿巡逻段也当成了 Segment**（因为它也有起止时间和路径点），于是行程链也收到了这些巡逻段。它们本是「物理巡逻」，却被行程链当「移动段」用。

## 二、第二课：为什么 visit 和 activity 永不重叠（好消息）

侦察的第一个发现，出乎我们意料：

> **你的两份真实数据里，停留段和出行段的重叠对数 = 0。**

2025 文件 30,682 个停留、26,843 个出行段；2026 文件 37,287 个停留、30,702 个出行段——**一个重叠的都没有**。

### 为什么会这样？

这不是巧合，是 **Google 数据模型的设计**。Google 把「你在停留」和「你在移动」设计成**互斥状态**：

- 记录员一次只记一种状态。你在移动，就没法同时「停留」。
- 两个停留之间必有出行段（或一个 gap），两个出行之间必有停留隔开。
- 时间上相邻的记录，要么无缝衔接（gap=0），要么中间有空档（正 gap），**绝无重叠（负 gap）**。

打个比方：电视机的频道。任一时刻屏幕上只有一个频道；频道 1（停留）播完切频道 2（出行），两个频道不可能同时 0:00–1:00 都在播。

### 所以呢（对产品的意义）

**好消息**：T29 行程链「取时间上紧邻的前驱/后继段」的配对逻辑，在**出行段层面是 100% 正确的**。它配对时担心的「两个段时间打架」的情况，在语义段层面根本不存在。

也就是说——**B5 最初想解决的问题（「visit 和 activity 重叠了怎么办」）是一个不存在的问题**。我们一度想修一个不存在的 bug。幸好先侦察了，没白开工。

## 三、第三课：ambient GPS——那个「勤快过头」的巡逻队（坏消息）

但如果语义段层面这么干净，那「重叠」从哪来？侦察第二次发现：**重叠全来自巡逻段（timelinePath-only traces）**。

### 3.1 巡逻段是什么

就是故事里的「巡逻本」：手机**每 2 小时**固定探查一次你在哪，写下一条 2 小时的 GPS 轨迹窗口。它有俩特点：

1. **它不看你在干嘛**。你睡觉、上班、长途开车，它都默默 2 小时巡逻一次。
2. **它只是一堆坐标**，没有「停留/移动」的语义。

这种记录在行业里叫 **ambient GPS（环境 GPS）**——不是因为你做了什么事才记录，而是**环境里一直在测**。Google 拿它干什么？主要是**确认主人的大致位置、校准语义判断**。它**不是**用来表达「你这段在移动」。

### 3.2 为什么巡逻段必然「撞」上停留段

这是**物理必然**，不是数据错误：

- 你一天有大量时间待在原地（家、办公室、表哥家）。
- 而巡逻队每 2 小时出动一次，**任何时候**停在原地的那 2 小时里，队列里必有一条巡逻记录盖在你头上。
- 所以「巡逻段时段 ⊇ 停留段时段」是常态。

数据印证：两份文件里 visit↔巡逻段的重叠对高达 **35,349 / 43,092**，中位重叠 **46.6 / 45.3 分钟**。注意最大重叠是**整整 120 分钟 = 巡逻窗口全长**——也就是说巡逻段的**大部分时间**常常整个盖在你的一次停留上（参见典型样本：巡逻 02:00–04:00 整个落在「00:50–06:40」的停留里）。

```
时间线示意（巡逻段 = █）：

停留 V1  ██████████████████████░░░░░░░░░░░░  00:50 → 06:40
巡逻 T1  ░░░░░░░░░░░░████████████░░░░░░░░░░  02:00 → 04:00（整段在 V1 里）

→ T1 物理上只是一段环境 GPS，语义上却落在一次停留中间
```

### 3.3 所以呢

- **对时间轴模式**：无害。巡逻点的 GPS 坐标是真实走过的位置，画线没问题。
- **对行程链**：**有害**。行程链把这 2 小时巡逻段当成「一次移动」去配对。于是出现了第三个发现。

## 四、第四课：三角现象——当巡逻队横跨两次停留

### 4.1 T29 行程链是怎么配对的

一句话：把所有停留和段**按时间排成一行**，每个停留取「它左边最近的一个移动段」做 incoming（怎么来的）、「右边最近的一个移动段」做 outgoing（怎么走的）。

```
V1 ······ S1 ······ V2 ······ S2 ······ V3
  ← S1    → S1              ← S2    → S2
  进来     出去               进来     出去
```

前提假设：**V1 结束 → S1 出发 → V2 到达 → S2 出发 → V3 到达**，一条干净的时间线。

### 4.2 巡逻段是怎么破坏这个假设的

巡逻段 T1 同时盖住 V1 和 V2（见第三课的示意）。在行程链的眼睛里：

- T1 的**时间起点**在 V1 中间 → T1 是「V2 的左邻居」→ 配成 V2 的 **incoming**；
- 但 T1 的**时间终点**在 V2 中间 → T1 又排在 V2 左边 → 同时也可能当 V1 的 **outgoing**（取决于更近的竞争者）。

结果：**同一个 T1 段，同时是 V1 的 outgoing 又是 V2 的 incoming**，而且它整段横跨在两次停留中间——这就是「**三角**」（back-to-back）现象。真实的人类轨迹应该是 V1 →（某真实移动）→ V2，但这个「真实移动」在语义段层面**没有记录**（Google 没判它是一次 activity），只有巡逻段横跨着。

看一下真实样本（2017-12-16，你的数据）：

| 角色 | 时间 | 时长 |
|------|------|------|
| 巡逻段 T1 | 02:00 → 04:00 | 固定在原地附近 |
| 停留 V1（from） | 00:50 → 06:40 | 5h50m 停留 |
| 停留 V2（to） | 01:49 → 04:36 | 2h47m 停留 |

行程链配出来的结果：「V1 →（移动 2 小时）→ V2」。**但真实世界不是这样**——V1 和 V2 时间上重叠了 4 个小时，不可能是「先待 V1 再移动到 V2」的前后关系。它们多半是**同一地点不同记录**（比如同一晚的两个候选标签），而那个「移动 2 小时」是巡逻队凭空填进去的假象。

### 4.3 规模有多大

| | 2025 | 2026 |
|---|-----:|-----:|
| 三角段数 | 9,558 | 11,117 |
| 占全部链移动段 | **~23%** | **~23%** |
| 三角中位重叠 | 11.9 min | 10.8 min |
| 出行段（真移动）里的三角 | **0** | **0** |

两个关键句：

1. **每 4-5 个链移动段里就有 1 个是巡逻假象**。这个比例不小，直接打脸「行程链 ≈ 旅行日记」的定位。
2. **三角 100% 来自巡逻段，真移动段一个都没有**。这告诉我们：**问题根源精准锁定，药方也精准**——只要不让巡逻段进链，三角直接归零。

### 4.4 用户实际感受

侦察的诚实结论：**多数三角涉及长停留（数小时）**，巡逻段是停留期间的环境 GPS。用户在行程链里看到的是「移动 02:00–04:00」配在两次数小时停留之间——**duration 显示偏大（2 小时窗口），distance 也不是真实旅途**，activityType 缺失显示成笼统「移動」。

这不算「错乱」，更像「颗粒度不对」：本应是「系统不知道你怎么从 A 到 B」，却显示成「你用了 2 小时从 A 到 B」。

## 五、所以，该怎么办？（决策分析）

### 5.0 问题定位在单一模式（by activity）

回到产品：`TripsPage` 有两个模式，代码里 `buildTripChain` **只在 `activityType` 模式计算**（`mode === 'activityType'`，timeline 模式读的是另一条 `prepareTimeline` 路径，从不碰链）。所以三角现象不是「两个模式共有」，而是**精确落在「按活动类型」模式这一个地方**：

| 模式 | 数据来源 | 巡逻段混入？ | 三角影响 |
|------|---------|:---:|:---:|
| 时间轴（默认） | `prepareTimeline`（物理点按时间合并排序去重） | 有点但只当坐标画线 | **无** |
| 按活动类型 | `buildTripChain`（拿 segments 配对成链） | 收到 activity + trace 两层段 | **有——23% 链移动段是假移动** |

对用户的意义：**你在「按活动类型」模式左栏看到的行程链，就是三角的展示现场**；切到时间轴模式看不到这个问题（因为那是另一套展示，读的是点不是链）。这条定位也意味着方案 A 的改动面收窄到单一路径：只要 `buildTripChain` 的输入侧过滤，就能修复这个模式的准确性，不影响时间轴的一行代码。

### 5.1 候选方案对比

| 方案 | 做什么 | 好处 | 代价 |
|------|--------|------|------|
| **A. 过滤巡逻段** | 行程链只收有语义的出行段，扔掉孤儿巡逻段 | 三角归零、时长/距离变准、逻辑最干净（「链 = 真实移动」） | **部分停留会缺 incoming/outgoing**（见 5.2） |
| B. 巡逻段降级展示 | 巡逻段留链，但标注「GPS 窗口」 | 保完整性 | UI 噪音大；本质是拿「物理巡逻」冒充「移动语义」，治标不治本 |
| C. 关闭收尾 | 认知入档，不动代码 | 零风险零投入 | 23% 假移动继续存在，但用户实际感受轻微 |

**我的评估**：B 是坏设计（把一个不属于语义层的东西硬塞进语义展示），直接排除。真正要权衡的是 A vs C。

### 5.2 方案 A 的代价——实测归零（重要修正）

> **⚠️ 本稿初版的「15-20% 缺口」是错误推理，已被 ledivedata 实测推翻。** 初版用「停留总数 − 过滤后链边数」估缺口（30,682 − 26,027 ≈ 4,655），**量纲是错的**：链边数是「段」的去重计数，一条 activity 段作为前停留的 outgoing + 后停留的 incoming 可服务两个「侧」，侧数与段数不可比。正确口径 = **两侧（incoming+outgoing）都为 null 的停留**。T33 对比脚本（`scripts/compare-chain-main-vs-branch.mjs`，全量扫描）实测：

| 指标 | main（现状） | branch（方案 A） |
|------|------------:|----------------:|
| 链边数 | 42,082 / 48,284 | 26,027 / 29,875（−38%，仅真移动） |
| **三角** | **12,037 / 15,517** | **0 / 0（✅ 归零）** |
| **孤立停留（incoming+outgoing 均 null）** | 0 / 0 | **0 / 0（✅ 无代价）** |
| 中位链时长 | 50.4 / 47.8 min | 15.0 / 14.8 min |
| ≈2h 假移动段数 | 19,891 / 22,701 | 75 / 75（基本清空） |

**结论反转：方案 A 几乎没有代价**——过滤巡逻段后并没有停留「失去全部连接」；每个停留至少一侧仍有真移动段可配（好数据：Google 的停留都有 activity 段接壤，巡逻段只是叠加在停留上的额外记录）。真正的卖点是**三角归零 + duration 从「2h 巡逻窗口」回到「真实移动时长」**。

所以 5.2 原来的产品取舍（「干净的链 + 孤立点 vs 全连接 + 假移动」）**不成立了**——现实是「干净的链 + 零孤立点」。这几乎是一边倒的改善，实验验证的价值从「测代价」变成「亲眼确认观感确实更好」。

### 5.3 我的建议（2026-09-15 修正版）

**开一个 `experiment/b5-livedata-overlap` 分支做方案 A**，因为：

1. **改动面极小**（已在 `buildTripChain` 内部用 `isActivityMovement` 过滤，仅改 3 文件）；
2. **效果干净且无代价**：三角归零、2h 假移动清空、中位时长从 ~50min 降到 ~15min；**isolated visits = 0**——没有任何停留丢失连接；
3. **你本地对比 main vs 分支，在「按活动类型」模式扫几个长停留密集的日子，确认观感改善**；
4. 失败也便宜：观感不可接受 → 分支作废，认知已完整入档。

```
Google 记录你生活的三种本子：
  visit（停留）        互斥 ←→  activity（出行）
                            ↑ 永不重叠（数据模型保证）
  两项都是「语义判断」
             │
             ▼
  timelinePath（巡逻）  每 2h 一次的 ambient GPS，纯物理坐标，无语义
                            ↑ 必然盖住你的停留（物理必然）

产品解析层把巡逻段也当成 Segment → 行程链（T29）收到两层段
  → 真移动段配对：100% 正确（零重叠）
  → 巡逻段配对：23% 的链移动是「2h 假移动」（三角现象，零来自真移动）

结论：
  ① 原假设「visit↔activity 重叠」= 不存在的问题（省了一次瞎开工）
  ② 真问题 = 巡逻段混入语义链，导致 1/4 边是假移动（duration 严重偏粗）
  ③ 药方 = 过滤巡逻段（A）→ 三角归零，实测代价为零（isolated stays = 0）
  ④ 分支已实现，等待你本地对比 main vs 分支的「按活动类型」列表观感
```

## 七、术语表

| 词 | 含义 |
|----|------|
| **semanticSegments** | Google Timeline 档案里的语义段数组，一条 = 一小段「你在做什么」 |
| **visit** | 停留段：有语义（topCandidate），起终点 + 地点标签 |
| **activity** | 出行段：有语义，起终点 + 交通方式（topCandidate.type），可带精细路径 |
| **timelinePath** | 一段 GPS 坐标轨迹。**带语义的段里** = 精细移动路径；**孤儿段** = 2h 巡逻窗口 |
| **timelinePath-only trace** | 只有 timelinePath、没有 visit/activity 语义的孤儿段 = ambient GPS 巡逻记录 |
| **ambient GPS** | 环境定位：不是因你的行为而记录，而是固定频率的环境探查 |
| **T29 行程链** | 「按活动类型」模式：把 visit + segment 按时间配对成「停留→移动→停留」日记 |
| **三角（back-to-back）** | 一个段同时是 V1 的 outgoing 和 V2 的 incoming，且横跨两者——巡逻段的典型产物 |
| **分支实验** | main=对照组、experiment/*=实验组、用户本地对比拍板 merge/关闭——替代无法做的 A/B |
